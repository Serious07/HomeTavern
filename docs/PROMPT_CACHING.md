# 🔧 Кэширование промптов для гибридных моделей

## 📋 Описание проблемы

При отправке **второго и последующих запросов** в одном диалоге с `llama-server`, сервер должен восстанавливать состояние из KV-кэша вместо полной перезагрузки промпта. Для моделей с архитектурой **qwen35moe** (гибридные MoE с рекуррентными слоями / Gated Delta Net) это критически важно.

### Симптомы проблемы
- Первый запрос: обработка промпта ~65–70 секунд ✅ (ожидаемо)
- Второй запрос (тот же диалог): снова ~65–70 секунд ❌ (должно быть <5–10 сек)

### Ключевые строки в логе llama-server
```
# ❌ Провал — кэш не восстановлен:
I slot update_slots: id 0 | task XXX | Checking checkpoint with [15824, 15824] against 15822...
W slot update_slots: id 0 | task XXX | forcing full prompt re-processing due to lack of cache data (likely due to SWA or hybrid/recurrent memory...)
W slot update_slots: id 0 | task XXX | erased invalidated context checkpoint

# ✅ Успех — кэш восстановлен:
I slot update_slots: id 0 | task YYY | Restored context checkpoint with [15824, 15824] against 15824...
```

---

## 🔬 Корневые причины

### 1. Расхождение позиций чекпоинтов
Разница в **даже 1–2 токена** между сохранённым чекпоинтом и текущим запросом приводит к полному сбросу кэша.

**Почему это критично для гибридных моделей**:
- Модели `qwen35moe` содержат рекуррентные слои (Gated Delta Net / SSM)
- Эти слои **не поддерживают частичное удаление последовательности** (`the context does not support partial sequence removal`)
- Рекуррентное состояние зависит от **точной позиции** каждого токена в потоке

### 2. Нестабильный префикс промпта между запросами
Если структура промпта меняется (системный промпт, профиль персонажа, форматирование истории), кэш не может быть восстановлен.

---

## ✅ Требования для стабильного кэширования

### 1. Используйте нативные флаги управления

```bash
# ✅ Правильно — нативный флаг:
--reasoning off

# ❌ Неправильно — устаревший способ, вызывает нестабильную токенизацию:
--chat-template-kwargs '{"enable_thinking":false}'
```

### 2. Не меняйте системный промпт между запросами в одной сессии

Системный промпт должен быть **бит-в-бит идентичным** во всех запросах внутри одного диалога.

### 3. Используйте правильные флаги запуска llama-server

```bash
llama-server \
  --model your-model.gguf \
  --port 1234 \
  --reasoning off \
  --no-context-shift \
  --slot-prompt-similarity 0.99 \
  --cache-ram 6144 \
  --cache-type-k q8_0 \
  --cache-type-v q8_0
```

| Флаг | Назначение |
|------|------------|
| `--reasoning off` | Отключает генерацию reasoning (стабильная токенизация) |
| `--no-context-shift` | Предотвращает сдвиг окна, который ломает рекуррентную память |
| `--slot-prompt-similarity 0.99` | Ужесточает порог схожести промптов (по умолчанию ~0.85) |
| `--cache-ram 6144` | Включает кэш промптов в RAM (6 ГБ) |
| `--cache-type-k q8_0 --cache-type-v q8_0` | Сжатие KV-кэша для экономии памяти |

### 4. Избегайте неподдерживаемых флагов

Не используйте `--swa-full` — данная модель не имеет поддержки в метаданных GGUF.

## 🛠️ Включение диагностики

### Шаг 1: Активируйте отладку

Добавьте или измените в `.env`:
```bash
ENABLE_PROMPT_DEBUG=true
```

Перезапустите сервер после изменений.

### Шаг 2: Отправьте два запроса в один диалог

Например, отправьте "Тест" дважды.

### Шаг 3: Проверьте лог

Консольный вывод:
```
[PromptDebug] [1716984000000-abc123] 🆕 First prompt for chat 1
[LLMService] Prompt debug: hash=abc123def456... length=15825 tokens=15825 match=—

[PromptDebug] [1716984060000-def456] ✅ chat=1 | len=15825 | hash=abc123def456... | tokens=15825
[LLMService] Prompt debug: hash=abc123def456... length=15825 tokens=15825 match=✅
```

Или подробный лог-файл `/tmp/hometavern_prompt_debug.log`:
```
[2026-05-30T03:00:00.000Z] — no-chat | len=15825 | hash=abc123def456... | tokens=15825 | sys=800 char=300 hero=200 hist=10 cur=50
[2026-05-30T03:01:00.000Z] ✅ chat=1 | len=15825 | hash=abc123def456... | tokens=15825 | sys=800 char=300 hero=200 hist=12 cur=50
```

### Интерпретация результатов

| Результат | Что означает | Действие |
|-----------|---------------|----------|
| `match=✅` | Промпт идентичен предыдущему | Кэш **должен** работать. Проверьте флаги llama-server |
| `match=❌` | Промпт изменился! | Найдите различия в логе частей промпта (system, charProfile, heroProfile) |
| `tokens=` разные значения | Разное количество токенов | Структура промпта нестабильна — проверьте историю диалога |

---

## 🔍 Анализ различий между запросами

Если `match=❌`, лог покажет детализацию:

```
[PromptDebug] ❌ Prompt CHANGED for chat 1: abc123def456 → def789abc012
[PromptDebug]   system=850, charProfile=300, heroProfile=200, history=12 msgs, current=50 chars
```

Сравните значения между запросами:
- **system** изменился? → Системный промпт модифицируется динамически
- **charProfile** изменился? → Профиль персонажа меняется
- **heroProfile** изменился? → Профиль героя пользователя меняется
- **history** (count) изменился? → Разное количество сообщений в истории

## 📊 Отладка токенизации

При включённой `ENABLE_PROMPT_DEBUG=true` также выполняется запрос к `/tokenize` endpoint llama-server. Это даёт:

```
first=[11, 248046, 5320, ...]    # Первые 10 токенов
last=[492, 13, 2]                # Последние 10 токенов
tokens=15825                     # Общее количество токенов
```

Сравнение `first` и `last` между запросами — самый надёжный способ убедиться в идентичности промптов.

---

## 🚨 Известные ограничения

1. **Гибридные модели** (qwen35moe) физически не поддерживают частичное восстановление контекста. Если промпты не идентичны — кэш **не может** работать.

2. **`--swa-full` недоступен** для данной модели (отсутствует в метаданных GGUF).

3. **Чекпоинты опциональны**: флаги `--checkpoint-every-n-tokens` могут отсутствовать в некоторых сборках llama.cpp.

## 📝 Рекомендации при полной нерешённости проблемы

Если после включения диагностики проблема сохраняется:

1. **Обновите llama.cpp** до последней сборки из master — улучшения кэширования регулярно добавляются
2. **Проверьте версию GGUF** модели — старые форматы могут иметь баги в рекуррентных слоях
3. **Попробуйте другую модель** той же архитектуры — для сравнения поведения
4. **Сократите контекст** — чем меньше промпт, тем выше шанс совпадения чекпоинтов
